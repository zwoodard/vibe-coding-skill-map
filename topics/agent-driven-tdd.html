Agent-Driven TDD

Combining test-driven development with AI agents: write specs, let the agent iterate until tests pass, and verify instead of trusting.

Why TDD + Agents Work Together

Test-driven development (TDD) traditionally struggles: tests are boring to write, and devs skip them. AI agents reverse this dynamic. Agents excel at generating code to pass a spec, and tests provide a concrete, measurable goal that agents can iterate toward without hallucinating.

  • Clear targets: Tests define exactly what "done" looks like
  • Self-correction: Agent runs tests, sees failures, tweaks code, re-runs
  • Protection: You verify behavior, not trust the agent's reasoning
  • Speed: Agents generate boilerplate and edge cases in seconds

The Red/Green Workflow

Red: Write minimal test specs (or let the agent draft them from requirements). Run tests; they fail.

Green: Hand the failing test output to Claude Code or Cursor. Say "make these tests pass." The agent generates code, runs tests, and iterates until green.

Refactor: You review the agent's code. Ask for optimizations or simplifications. Verify tests still pass.

This replaces the traditional solo developer loop, but with AI handling the tedious implementation.

Best Practices

Write clear test specs: Use descriptive test names and comments. Bad test: test_thing(). Good: test_validates_email_format_and_rejects_duplicates().

Include edge cases in tests: Tell the agent or the test suite to cover nulls, empty strings, large inputs. Tests guide the agent toward robustness.

Use deterministic tests: Avoid flaky time-based or random tests. Agents struggle with non-determinism.

Set test scope: Focus on behavior, not implementation. Let the agent optimize the details.

Integrate with CI: Each push runs tests and blocks merges on failure. Agents still need to pass CI gates.

CI Gates Still Apply

Agent-generated code should pass the same CI checks as human-written code — full test suite, linters, security scans. No exceptions. The agent passing tests locally is a good sign, but CI is the real verification. If it doesn't pass CI, it doesn't merge.

Common Pitfalls

Over-specifying: Too many micromanagement tests slow the agent. Let it find the simplest solution that passes.

Brittle tests: Tests that check implementation details (e.g., "must use map()") instead of behavior break when agents optimize.

Ignoring flakiness: If a test sometimes passes and sometimes fails, the agent can't hit a stable target. Fix flaky tests first.

No feedback loop: Always show the agent test output. It can't self-correct without seeing what broke.

Tip: Start with a simple, high-value feature (maybe 20–50 lines). Write 3–5 test cases. Hand off to Claude Code with make these tests pass. Review the result. This pattern scales to entire modules.
