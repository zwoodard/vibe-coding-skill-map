Memory & State Management

Enable agents to remember past interactions, maintain state across sessions, and build on previous work.

Session vs. Long-Term Memory

Session memory is short-lived: the conversation history of a current interaction. An agent receives a user request, reasons about it, accesses current session memory, and responds. When the session ends, that memory is discarded. Long-term memory persists across sessions: notes, learned facts, user preferences, past debugging insights.

Session memory is implicit (the conversation itself). Long-term memory requires explicit storage and retrieval. A debugging agent might note in long-term memory: "User's database has a connection pool issue that requires timeout=30s." In a future session with the same user, the agent retrieves that note and avoids the same problem.

CLAUDE.md: Project-Level Instructions

CLAUDE.md files are persistent, human-editable markdown files that live in your project. Claude reads them at the start of every session and injects them into the system prompt. Use CLAUDE.md for stable, reusable instructions that apply across many sessions.

Example CLAUDE.md entries: "Use async/await, not callbacks in JavaScript. Always test with pytest. Document new functions with docstrings. If you encounter database errors, check the connection pool."

The Claude Agent SDK automatically re-reads CLAUDE.md after context compaction, ensuring these instructions stay active even on long-running tasks. Keep CLAUDE.md concise (under 2000 words); it goes into every request, so brevity is important.

Auto-Memory & Learning from Corrections

Auto-memory lets Claude accumulate knowledge as it works. When you correct Claude's behavior ("Actually, use the newer API"), Claude can save that insight to auto-memory without you writing anything. Subsequent sessions retrieve and apply these learnings.

Auto-memory stores notes like: "Build command for this project is `npm run build && npm test`, not just `npm run build`." "The user prefers TypeScript interfaces over types." These notes improve Claude's future performance on the same project without manual updates.

Shared Memory Across Agents

In multi-agent systems, agents need to share findings and state. Implement a shared memory store (file system, database, key-value store) that all agents can read and write. A researcher agent stores findings in shared memory; a code generator reads them and incorporates requirements. A reviewer reads both and provides feedback.

Key pattern: use structured keys like shared/task-id/findings.json or shared/user-123/preferences.json. Agents lock memory for writes to prevent conflicts. Use version IDs or timestamps to track updates. Clear stale memory periodically to avoid bloat.

Memory Retrieval Patterns

How do agents retrieve the right memory at the right time? Explicit retrieval: an agent reads a specific memory file by key. Semantic search: an agent queries a vector database with an embedding ("debugging tips for database timeouts") and retrieves similar notes. Hierarchical: agents first check local memory (session-specific), then shared memory (task-specific), then long-term (project-wide).

For large amounts of memory, semantic search (using embeddings) scales better than keyword search. Store memory as structured JSON with embeddings, then query by similarity.

Practical Implementations

Claude API Memory Tool: Use the memory tool to create, read, update, and delete files in a memory directory. Your application handles storage (local filesystem, cloud bucket, database). The agent makes tool calls; your app executes them. Full control over storage location and retention. Session-based (LangGraph): Use thread-scoped checkpointers to maintain conversation history within a session. Upgrade to MongoDB or other backends for persistent, cross-session memory.

Managed services: Amazon Bedrock AgentCore Memory automates memory extraction and consolidation. Microsoft Foundry Agent Service provides a managed long-term memory layer. These reduce operational burden but reduce flexibility.

Context Compaction & Cleanup

Long conversations accumulate token cost. Implement context compaction: as conversation history grows, summarize old turns (keeping essential facts), then remove the raw history. The SDK handles this automatically, but you should design your memory strategy to complement it.

Example: summarize "User debugged database issue. Solution: set timeout=30s in connection pool" from 500 tokens of back-and-forth into 50 tokens. Store this summary in long-term memory. Later agents retrieve the summary instead of the full conversation.

Also clean up stale memory. If memory is older than 6 months and irrelevant to current work, delete it. This keeps memory stores lean and retrieval fast.

Pro tip: Treat memory as a knowledge base. Index it, make it searchable, archive old entries. Bad memory management can become a bottleneck as agents accumulate experience.
