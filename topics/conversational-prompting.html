Conversational Prompting

How to ask AI good questions and get reliably useful answers.

The Golden Rule: Specificity

Vague prompts produce vague answers. The best prompts include success criteria (what "done" looks like) and an output contract (format, length, tone, what sections you need).

Instead of: "Write code to sort a list"

Try: "Write a Python function that sorts a list of dicts by the 'age' key in descending order. Return a 20-line function with docstring and type hints."

Provide Context Upfront

AI models work best when they understand your situation. Include:

  • What you're trying to accomplish (not just the immediate task)
  • What tools/languages you're using
  • Relevant code snippets or examples
  • Constraints (budget, performance, dependencies)
  • What you've already tried

Paste your error message, logs, or failing tests. Context is often worth 100 follow-ups.

Iterate with Follow-Ups

Treat it like a conversation. After the AI responds:

  • Ask it to explain parts you don't understand
  • Ask for different approaches (faster, simpler, more robust)
  • Ask it to refactor or optimize its own suggestion
  • Push back: "That won't work because..." and let it revise

Each follow-up helps the model refine understanding of your actual problem.

Common Mistakes

  • Too vague: "How do I debug this?" (no error, no context)
  • No context: Asking to write code without naming libraries, frameworks, or constraints
  • Single-shot: Expecting perfect output on the first try instead of iterating
  • Ignoring format: Not specifying if you want JSON, markdown, code, or prose
  • Sharing secrets: Pasting API keys, passwords, or proprietary data into prompts

Model Flavors

Frontier models from OpenAI, Anthropic, and Google are largely interchangeable for everyday coding tasks. The more useful distinction is between model modes:

  • Thinking / reasoning models: Spend extra time "thinking" before responding. Better for complex logic, multi-step problems, architecture decisions, and tricky bugs. Use when correctness matters more than speed.
  • Non-thinking / fast models: Respond quickly with no extended reasoning step. Great for boilerplate, simple edits, explanations, and high-volume tasks where latency matters.

Pick the mode that fits the task. Use thinking mode for hard problems, fast mode for everything else. The specific provider matters far less than matching the right mode to the job.

Pro Tips

  • Use templates—if you find a prompt that works, save it and reuse it
  • Show, don't tell: paste examples of the output format you want rather than describing it
  • For code, ask for edge case handling and tests alongside the implementation
  • When results are off, add constraints ("under 50 lines", "no external dependencies") rather than re-explaining the goal
  • Never paste production secrets, customer data, or unpublished code
