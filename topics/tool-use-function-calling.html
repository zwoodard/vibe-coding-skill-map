Tool Use & Function Calling

How AI models request external tools and data systems to solve problems beyond their training data.

What Is Tool Calling?

Tool calling (also called function calling) is the mechanism that lets AI models request execution of code, APIs, or databases instead of trying to answer from memory. The model doesn't actually execute the tool—it describes what it wants to call and with what parameters. Your application receives that request, runs the tool, and returns results. This creates a loop: model → request → execute → response → model continues reasoning.

Key insight: The model decides which tool to call based on the task context. You provide the schema; the model decides if/when to use it.

The Request-Response Pattern

Tool calling follows a clear cycle: The model analyzes the user's request, examines available tools and their descriptions, decides which tool(s) to invoke with specific parameters, and returns a formatted request (not execution). Your application then:

  • Parses the tool request and validate inputs
  • Execute the actual tool/function/API call
  • Capture the result (success or error)
  • Send the result back to the model
  • Model incorporates the result into its reasoning and continues

This loop repeats until the model decides it has enough information to answer the user's question.

Defining Tool Schemas with JSON

Each tool must be defined with a JSON schema that tells the model its name, purpose, and expected parameters. A typical schema includes the tool name (descriptive, no spaces), a detailed description of what it does and when to use it, and a parameters object defining each input field with type, description, and whether it's required. The model reads this schema to understand tool capabilities without seeing implementation details.

For example, a search_wikipedia tool has parameters like query (required string) and language (optional, default English). The description is crucial—models use it to decide whether the tool fits the current task. Heavily nested schemas reduce quality; flatten complex parameters where possible. Aim for fewer than 20 tools available at once to avoid context bloat.

How Models Decide Which Tool to Call

Models use context, available tools, and task requirements to select the right tool. A question like "What's the temperature in Tokyo?" triggers selection of a weather API tool. A math problem might skip tool calling and compute directly. Models reason probabilistically based on training—good descriptions and examples teach them when to use each tool.

As of 2025, structured outputs (via strict: true in tool definitions) guarantee that tool calls match your JSON schema exactly. This eliminates parsing errors and invalid parameter types, making production systems more reliable.

Error Handling & Retries

Tool calls can fail: invalid parameters, network errors, API rate limits, missing data. Best practice is to return the error to the model (e.g., "Tool search_db returned: connection timeout"). The model then either retries with adjusted parameters, tries a different tool, or explains to the user that the task can't be completed. Never silently drop errors—models need visibility to reason about failures.

For resilience, implement exponential backoff for transient errors, validate tool inputs before execution, and set timeouts on external calls. Log all tool invocations for debugging and auditing.

Practical Workflow

1. Define 5-10 core tools your app needs (database query, file read, web search, email send, etc.). 2. Write JSON schemas for each, with clear names and descriptions. 3. Implement tool execution logic in your application. 4. Use Structured Outputs to enforce schema compliance. 5. Test each tool independently, then test with the model selecting and chaining them. 6. Monitor tool call patterns in production to identify missing tools or confusing descriptions.

Pro tip: Start with 3-5 essential tools. Add more incrementally. Each tool increases decision latency and context usage.
