Markdown Specifications & PRDs

Writing specs that AI can understand and execute with precision

Why Markdown for Specs?

Markdown is the ideal format for specifications in AI-driven development because it's both human-readable and machine-parseable. Unlike Word docs or PDFs, Markdown is version-controllable in Git, making specs evolve alongside code. AI models understand Markdown structure (headers, lists, code blocks) better than unstructured prose, enabling more accurate interpretation of requirements.

A Markdown spec becomes a single source of truth that stays current, enables diffing to track requirement changes, and integrates seamlessly with your development workflow.

Core Spec Structure

  • Goal & Problem Statement: One-liner describing what you're building and why. Keep this tight.
  • Requirements: Functional and non-functional needs. List each distinctly.
  • Acceptance Criteria: Testable outcomes. "User can login" is vague; "User enters email/password and receives session token" is not.
  • Constraints: Explicit boundaries—what NOT to build. This prevents AI from gold-plating features.
  • Technical Notes: Dependencies, APIs, third-party integrations, performance targets.
  • Success Metrics: How will you know it works? Response time, error rate, user actions?

Practical Spec Template

Use this structure for every spec you hand to an AI agent:

# Feature: [Feature Name]
## Goal
[One-liner with problem statement]
## Requirements
- [Requirement 1]
- [Requirement 2]
## Acceptance Criteria
- [ ] Criteria 1
- [ ] Criteria 2
## Constraints
- Do NOT [Thing]
- Must use [Technology]
## Technical Notes
[Details on architecture, dependencies]

AI agents respond better to checklists and explicit boundaries than to narrative prose. Use bullet points liberally.

Explicit Boundaries Matter Most

State what NOT to implement. If you don't say "don't add email validation," an AI might add it anyway because most applications require it. Explicit negatives prevent scope creep and wasted token usage.

Example: "Build a notes API. Constraints: Do NOT add user authentication. Do NOT implement sorting or filtering." These statements keep the AI focused and prevent unnecessary complexity.

Linking Specs to Execution

Hand the spec directly to Claude Code or your AI tool. In the conversation, reference the spec file: "Implement the feature in notes.md" or paste the spec into the prompt. This gives AI the exact requirements without ambiguity.

After implementation, update the spec to mark completed criteria and note any design decisions that changed. Keep specs as living documents—they become institutional knowledge for future work.

AI-Optimized Specifications

Structure multi-phase specs with clear dependencies and testable outcomes. Break complex features into bounded phases with sequential steps. Define "done" for each phase before moving to the next.

Anthropic's best-practices guide for Claude Code identifies six areas that effective project context should address: commands with flags, testing expectations, project structure, code style with examples, git workflow, and explicit boundaries. Address all six and AI will execute with minimal back-and-forth.
