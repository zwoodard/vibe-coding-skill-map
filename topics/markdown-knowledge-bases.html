Markdown Knowledge Bases

Organize project knowledge so AI agents understand your patterns

Why Markdown Knowledge Bases?

For 95% of teams, Markdown-based knowledge bases beat complex RAG (Retrieval-Augmented Generation) systems. They're simpler, version-controlled, always current, and AI-readable.

A knowledge base is a collection of Markdown files that document your project conventions, architecture decisions, how-to guides, and API specs. It's your team's shared brain, searchable and accessible to both humans and AI.

Markdown vs. RAG: Why Markdown Wins

Markdown: Easy to write, version-controlled in Git, human-readable, always up-to-date, no infrastructure, AI-friendly.

RAG: Requires vector databases, embedding models, retrieval pipelines, and maintenance. Overkill for most teams. Better suited for massive, constantly-growing knowledge (like all of Wikipedia).

Unless your knowledge base is thousands of documents and growing daily, Markdown is the right choice. It's also more accessible: search for files, read them directly, edit easily.

Knowledge Base Structure

  • docs/conventions/: Code style, naming patterns, naming conventions, error handling approach.
  • docs/architecture/: System design, module relationships, data flow, key components.
  • docs/decisions/: ADRs (Architecture Decision Records). Why did you choose framework X over Y? Document it.
  • docs/how-to/: Step-by-step guides for common tasks: "How to add a new API endpoint," "How to add a new page."
  • docs/api/: API specifications, endpoint documentation, authentication details.
  • docs/gotchas/: Known issues, quirks, workarounds. "We use this weird hack for reason X."

Keep docs close to code. Place them in your repo's docs/ folder, not in a wiki you need to login to access.

Making Docs AI-Readable

Write for both humans and AI. Use clear headers and structure. Example of an AI-friendly API doc:

# POST /api/users

## Purpose
Create a new user account

## Request
- email: string (required)
- password: string (required, min 8 chars)

## Response
- id: number
- email: string
- createdAt: ISO timestamp

## Errors
- 409: Email already exists
- 400: Invalid password

This structure is easier for AI to parse and use.

Convention Documents

Document your code style, naming conventions, and patterns. When the AI knows "We name tests as *.test.ts and use describe/it blocks," it generates code matching your style.

Example convention doc:

# Code Conventions

## Testing
- Files: *.test.ts
- Framework: Jest
- Pattern: describe/it

## Error Handling
- All endpoints catch errors and return { error: string, code: string }
- Use custom error classes

Architecture Decision Records (ADRs)

An ADR documents a decision: "We chose PostgreSQL over MongoDB because..." ADRs are gold for AI context. They explain the "why" behind choices, preventing the AI from second-guessing decisions.

ADRs are lightweight: title, context, decision, consequences. One page per decision. Over time, they become a searchable history of your technical evolution.

How-To Guides

Step-by-step guides for common tasks speed up onboarding—both for humans and AI. "How to add a new API endpoint" means new developers (and new AI sessions) don't re-invent the wheel.

Guides should be concrete: actual code examples, exact command sequences, common pitfalls. Not abstract advice—practical walkthroughs.

Versioning & Maintenance

Keep docs in Git alongside code. When code changes, update docs. Review doc PRs like code PRs. Old, stale docs are worse than no docs—they mislead.

Set a quarterly doc review: are these still accurate? Remove outdated docs. Add docs for patterns that are missing.

Linking Docs to AI Sessions

In CLAUDE.md, reference your knowledge base: "For API conventions, see docs/api/conventions.md." When starting a session, point the AI at relevant docs: "Read docs/how-to/add-endpoint.md then implement this feature."

This technique saves tokens and ensures the AI follows your established patterns.
